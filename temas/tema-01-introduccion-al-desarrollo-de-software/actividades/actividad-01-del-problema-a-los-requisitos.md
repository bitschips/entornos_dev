# Actividad 01. Del problema a los requisitos

[Volver al índice de actividades](README.md) · [Volver al tema](../tema-01.md)

**RA:** RA1.b y RA1.g · **Duración orientativa:** 45–60 minutos · **Formato:** parejas.

## Objetivo

Reconocer que un producto de software comienza por resolver una necesidad, no por elegir un lenguaje o un editor.

## Situación de partida

El centro quiere una aplicación web sencilla para reservar equipos portátiles. Una persona elige un equipo y un intervalo horario; el sistema debe impedir reservas simultáneas del mismo equipo.

## Instrucciones

1. Identifica **tres perfiles** que usarían o administrarían la aplicación.
2. Redacta **cinco requisitos funcionales** y **dos no funcionales**. Ejemplo funcional: «El usuario puede consultar las franjas libres». Ejemplo no funcional: «La interfaz debe poder utilizarse desde un móvil».
3. Escribe **dos historias de usuario** usando: «Como [rol], quiero [acción] para [objetivo]».
4. Elige una historia y define **tres criterios de aceptación** medibles; incluye un caso de reserva repetida.
5. Divide el trabajo en las fases **análisis, diseño, codificación, pruebas, despliegue y mantenimiento**. Señala una evidencia o producto para cada fase.
6. Propón una primera versión mínima (MVP) que pueda entregarse y evaluarse en una iteración.

## Evidencias

- Fichero Markdown o PDF generado a partir de un editor, con requisitos, historias, criterios y fases.
- Diagrama propio de flujo o boceto de la pantalla (captura o dibujo legible).
- Una reflexión de 3–5 líneas: «¿Qué riesgo tiene programar sin validar requisitos?».

## Comprobación / criterios

- [ ] Los requisitos son concretos y no contradictorios.
- [ ] Los criterios de aceptación son verificables.
- [ ] El flujo contempla impedir doble reserva.
- [ ] Las seis fases se relacionan con productos reales.
- [ ] El MVP evita funciones innecesarias.

**Ampliación:** simular un cambio de requisito y explicar qué entregables habría que revisar.
